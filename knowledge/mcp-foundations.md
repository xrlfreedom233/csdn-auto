# MCP 基础知识

Model Context Protocol（MCP）用统一协议连接 AI 应用与外部数据、工具和工作流。MCP 采用客户端—服务端架构：Host 是面向用户的 AI 应用，Host 中的 MCP Client 与一个 MCP Server 建立会话，Server 向 Client 暴露能力。通信消息使用 JSON-RPC。

Server 的三类常见能力有 Tools、Resources 和 Prompts。Tools 是模型可发起调用的操作，应使用清晰的名称、描述和输入 schema；Resources 向应用提供可读取的上下文，通常由 URI 标识；Prompts 是用户可显式选择的模板化消息或工作流。应根据语义选择能力，不要把只读资料强行设计成有副作用的 Tool。

stdio 传输适合由 Host 在本机启动子进程的场景。Server 的标准输出用于协议消息，调试日志应写到标准错误，否则可能破坏通信。Streamable HTTP 适合远程服务，远程部署时还需考虑认证、授权、会话管理、限流和超时。

# MCP 安全边界

Tool 的参数 schema 只是结构约束，不能代替服务端校验和授权。Server 必须把模型传入的文本视为不可信输入，对文件路径、URL、SQL、Shell 参数和资源标识符进行约束。高风险或不可逆操作应显示具体影响，并在执行前要求用户确认。服务不应因为请求来自 AI 应用就默认它可信。

远程 MCP Server 应对每次请求执行授权检查，不能只判断用户是否已登录。凭据不应出现在日志、Tool 返回值或模型上下文中。审计日志应记录谁在什么时间调用了哪个 Tool、关键资源范围与结果状态，同时对敏感字段脱敏。

# RAG 与 MCP

RAG 的基本链路是文档解析、切块、建立索引、召回、可选重排，最后把少量相关片段与来源一起交给模型。切块大小应保留语义完整性，同时避免不相关内容占用大量上下文。检索结果需保留来源元数据，才能支持引用和排错。

可以把知识检索封装成 MCP Tool，由模型根据任务决定何时检索；也可以由 Host 在调用模型前主动检索。前者更灵活，但需要控制调用次数和权限；后者的流程更简单、可预测。不论使用哪种方式，检索文档都是不可信数据，其中的指令不应覆盖系统规则。
